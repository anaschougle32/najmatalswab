# Najmat Alswab Website — Discovery, Design and Architecture Proposal

## Executive decision

The profile supports a focused positioning: **Dubai-based technical services company with a 5,700 sq. ft. production facility in Umm Al Quwain, centered on steel-product installation, maintenance, custom fabrication, architectural metalwork, and building services.**

The website should not imitate the presentation. It should translate its strongest signals—blue-and-gold identity, metal materiality, architectural geometry, production capability, and technical specificity—into a quieter, more credible digital system.

No production code should begin until the company confirms the factual risks and the implementation platform decision at the end of this proposal.

## 4. Recommended visual direction

**Direction: “Fabrication Drawings, Finished Surfaces.”**

The experience combines the discipline of a technical drawing with the tactile quality of finished metal:
- Large, rights-cleared images of fabrication, machinery, joints, facades, and installed architectural metalwork.
- Fine datum lines, measurements, captions, and material labels used only where they add information.
- Asymmetric editorial compositions inspired by sheet-metal cuts and facade bays.
- Predominantly white and cool-metal surfaces, interrupted by deep blue structural bands and small yellow-gold signals.
- Minimal rounded corners, no glass effects, no gradient text, no floating decorative shapes, and almost no shadow.
- Motion limited to image reveals, navigation state changes, gallery transitions, and functional feedback; disabled when reduced motion is requested.

The memorable idea is **the transition from raw material and process to finished architectural detail**.

## 6. Typography

- **Primary UI and body:** IBM Plex Sans—technical, highly readable, and less generic than Inter.
- **Display and headings:** Archivo—condensed enough to feel engineered without becoming stereotypically industrial.
- **Arabic companion:** Noto Sans Arabic, matched by weight and hierarchy.
- **Numerals/specifications:** IBM Plex Mono in small doses for dimensions, material grades, dates, and machine data.
- Body text should remain sentence case. All caps is reserved for short drawing labels or navigation states.
- Blog reading width: approximately 68–72 characters per line with generous line height.

## 7. Layout system

- **Maximum content width:** 1,440 px; readable text columns capped around 720 px.
- **Grid:** 12 columns desktop, 8 tablet, 4 mobile.
- **Header:** approximately 80 px desktop and 64 px mobile; logo, primary navigation, language-ready slot, and one “Send project inquiry” action.
- **Spacing:** broad section rhythm without enclosing every section in a container; denser rhythm for specifications and admin screens.
- **Desktop:** alternating full-width image fields and precise editorial columns—not repetitive three-card rows.
- **Mobile:** deliberate image crops, stacked specification tables, full-width form actions, and a compact navigation drawer that retains the company name.
- **Borders/radius:** straight edges or 2–4 px radius; hairline dividers; no decorative shadows.
- **Accessibility:** visible focus treatment, semantic landmarks, keyboard operation, text alternatives, and reduced-motion support.

## 12. Admin architecture

- **Authentication:** email/username plus Argon2id password hash, server-side session, secure HttpOnly/SameSite cookies, CSRF defence, login throttling, session expiry, and logout revocation.
- **Dashboard:** practical work queue—new inquiries and recent drafts; no decorative analytics.
- **Publishing:** Markdown editor, side-by-side preview, autosaved draft, cover/inline media picker, category/tags, slug, SEO fields, publish/unpublish, deletion confirmation.
- **Inquiries:** searchable/filterable table, detail view, status change, private notes, spam deletion, CSV export.
- **Media:** validated upload, metadata/alt text, usage reference, and copyable URL.
- **Authorization:** one admin role initially; roles should be added only if a real second permission level is required.
- **Auditability:** timestamps and author/editor references; a full revision-history system is deferred unless required.

## 13. SQLite schema

```text
admins
- id, email UNIQUE, password_hash, display_name, is_active
- created_at, updated_at, last_login_at

sessions
- id, admin_id FK, token_hash UNIQUE, csrf_secret_hash
- expires_at, created_at, revoked_at

posts
- id, title, slug UNIQUE, excerpt, content_markdown
- cover_media_id FK NULL, author_admin_id FK
- category_id FK NULL, status CHECK(draft,published,archived)
- seo_title, seo_description
- published_at, created_at, updated_at

categories
- id, name, slug UNIQUE, description, created_at, updated_at

tags
- id, name, slug UNIQUE, created_at

post_tags
- post_id FK, tag_id FK, PRIMARY KEY(post_id, tag_id)

media
- id, github_path UNIQUE, public_url, filename, mime_type
- byte_size, width, height, alt_text, uploaded_by FK
- created_at

inquiries
- id, reference UNIQUE, name, company, email, phone
- inquiry_type, project_type, project_location, subject, message
- source_page, status, attachment_media_id FK NULL
- created_at, updated_at

inquiry_notes
- id, inquiry_id FK, admin_id FK, note, created_at

login_attempts
- id, identity_hash, ip_hash, succeeded, created_at
```

- Foreign keys enabled; indexes on post status/published date, inquiry status/date/email, category slug, and tag slug.
- Parameterized queries and transactions for publishing, media records, and destructive actions.
- A migration table records applied migrations.
- Inquiry text and uploaded media limits enforced in the database and application.

## 14. GitHub media architecture

```text
Browser → authenticated application server → validation/optimization → GitHub Contents API
                                                        ↓
                                            SQLite media reference
```

- Server-only variables: `GITHUB_TOKEN`, `GITHUB_OWNER`, `GITHUB_REPOSITORY`, `GITHUB_BRANCH`, `GITHUB_IMAGE_PATH`.
- Token scoped to contents write access on one dedicated repository; never delivered to the browser or logs.
- Paths: `/images/pages`, `/images/blog`, `/images/uploads`, and `/images/inquiries` only if client attachments are intentionally public.
- Safer recommendation: **do not store confidential inquiry attachments in a public GitHub repository**. Use a private repository with authenticated retrieval or a VPS-private directory. This must be decided before attachments are enabled.
- Validate MIME signature and extension, reject executable/polyglot files, cap dimensions and size, normalize orientation, strip metadata, create WebP derivatives where suitable, and generate collision-resistant safe filenames.
- SQLite stores paths, URLs, dimensions, MIME type, alt text, and uploader—not binary data.
- Deletion should check usage first and remove both GitHub object and database reference in a recoverable workflow.

## 15. Technical stack

### Requested portable production stack
- React + TypeScript frontend.
- Node.js + Fastify application server.
- SQLite with Drizzle ORM and versioned migrations.
- Markdown storage with a sanitizing semantic renderer.
- Zod validation shared where appropriate, with server validation authoritative.
- Argon2id password hashing and server-side session records.
- GitHub API through the server only.
- Vite for the public/admin frontend; server-rendered metadata or pre-rendering must be added for strong per-page SEO.
- Vitest for unit/integration tests and Playwright for browser flows.

### Important platform constraint
This Lovable project is a client-side React/Vite application and cannot run a persistent Node server or SQLite database. Lovable’s supported persistent backend would require Lovable Cloud, which the brief explicitly forbids. Therefore:

- The **public frontend and admin interface shells** can be designed here.
- A **working SQLite CMS, custom authentication, inquiry API, secure GitHub uploads, and VPS runtime cannot be completed inside this hosted Lovable project**.
- The full system requires a separate standard Node/VPS codebase or migration outside the Lovable runtime. Pretending otherwise would produce an insecure or nonfunctional implementation.

## 16. Deployment architecture

```text
Internet
   ↓ HTTPS
Nginx or Caddy
   ↓
Node/Fastify application (systemd or Docker)
   ├── React public site and admin assets
   ├── Auth, blog, inquiry and media APIs
   ├── SQLite database on persistent volume
   └── Private upload staging directory
                ↓ server-side only
          GitHub Contents API
```

- Node LTS, HTTPS, secure headers, request-size limits, rate limiting, structured logs, and process supervision.
- SQLite in WAL mode with one application writer, regular integrity checks, and migrations before restart.
- Nightly encrypted database backup plus periodic restore tests; retain multiple daily/weekly copies off-server.
- Back up environment configuration securely and rely on the GitHub repository for media history.
- Deployment documentation should cover environment variables, admin bootstrap, migrations, build/start, reverse proxy, HTTPS, logs, rollback, and backup restore.
